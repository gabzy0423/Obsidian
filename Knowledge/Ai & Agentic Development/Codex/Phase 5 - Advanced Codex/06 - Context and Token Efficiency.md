# 1. Introduction

AI coding agents depend on context to understand projects and perform tasks. Context may include developer instructions, documentation, source code, conversation history, tool results, errors, test output, and architectural decisions.

More context does not automatically improve results. Excessive or irrelevant material can waste tokens and time, introduce conflicting instructions, repeat investigations, and distract from the task.

**Context and Token Efficiency** means providing the information an agent needs while minimizing unnecessary material.

## Core Principle

**The objective is not to minimize tokens at all costs. It is to maximize the relevance, accuracy, and usefulness of the context.**

A short prompt missing requirements may be less efficient than a longer prompt containing the right constraints.

# Part II — Context Fundamentals

## 3. What Is Context?

In AI-assisted development, **context** is the information available to the model while it processes a task.

For “Fix the login validation bug,” useful context may include the login controller, validation rules, related authentication services, project instructions, error details, and relevant tests. The agent likely does not need every frontend component, unrelated migrations, or old logs for another feature.

~~~text
Developer Request
        |
        v
Project Instructions
        |
        v
Relevant Source and Documentation
        |
        v
Tool Results and Tests
        |
        v
AI Agent → Task Execution
~~~

Relevant context helps the agent reason; irrelevant context creates unnecessary work.

---

## 4. What Is a Context Window?

A **context window** is the amount of information a model can consider during a generation request. It is measured in tokens.

~~~text
+---------------------------------------+
|            Context Window             |
+---------------------------------------+
| System and Developer Instructions     |
| Project Instructions                  |
| Conversation History                  |
| User Request                          |
| Source Code and Tool Results           |
| Generated Output / Reasoning Budget   |
+---------------------------------------+
~~~

Limits vary by model and runtime. Not all context is visible to a developer. A large window does not remove the need to select useful context.

**Misconception:** A large context window means the entire repository should always be provided. Unnecessary information can increase processing and distract from the task even when it fits.

---

## 5. What Are Tokens?

Tokens are units used by language models. A token can represent a word, part of a word, punctuation, whitespace patterns, code fragments, or other encoded content.

~~~text
public class MainActivity
~~~

The exact number of tokens depends on the tokenizer and model. Tokens are not equivalent to words, characters, or lines of code; do not estimate usage solely from line counts.

---

## 6. Types of Token Usage

| Category | Description |
|---|---|
| Input tokens | Information supplied to the model |
| Output tokens | Information generated by the model |
| Reasoning tokens | Internal reasoning usage where applicable |
| Cached input tokens | Reused input processed through supported caching |

Usage and billing depend on model, runtime, subscription, and API arrangement. Do not assume all Codex environments expose identical accounting.

# Part III — Context Quality

## 7. Relevant vs Irrelevant Context

Relevant context materially affects requirements, implementation, architecture, verification, security, or scope. Relevance depends on the task, not just on whether a file is in the same repository.

For an Android sign-in alignment issue:

| Information | Relevance |
|---|---|
| Sign-in XML layout | High |
| Referenced drawable resources | High |
| Relevant theme and dimensions | High |
| Applicable UI standards | High |
| Firebase database schema | Usually low |
| Entire Git history | Usually low |
| Unrelated dashboard controllers | Low |

---

## 8. The Context Selection Principle

Before adding information, ask:

1. Does it affect the requested task?
2. Is it necessary to understand a dependency?
3. Is it an authoritative source?
4. Is it current?
5. Can the agent retrieve it when needed?
6. Is it already included elsewhere?

~~~text
Candidate Information → Relevant?
                       ├── No: Exclude
                       └── Yes: Authoritative and current?
                                ├── No: Verify source
                                └── Yes: Include or reference
~~~

Preserve essential constraints even if they are not visible in the file being edited.

# Part IV — Prompt Optimization

## 9. Why Prompt Structure Matters

A vague prompt forces the agent to infer what should change, which files matter, what must remain unchanged, what is out of scope, and how completion should be verified.

Weak:

~~~text
Fix my login.
~~~

Better:

~~~text
Task:
Fix the sign-in screen alignment.

Scope:
Android XML layout and directly related UI resources.

Constraints:
- Follow AGENTS.md.
- Do not modify Firebase authentication logic.
- Do not add UI libraries.
- Preserve existing functionality.

Verification:
Check constraints and resource references.
Report any verification that could not be performed.
~~~

The longer prompt is more efficient if it reduces uncertainty and rework.

---

## 10. Recommended Prompt Structure

~~~markdown
## Objective
## Scope
## Relevant Context
## Constraints
## Expected Output
## Verification
~~~

Example:

~~~text
Objective:
Investigate a Laravel schedule validation issue.

Scope:
ScheduleController and directly related validation and service logic.

Context:
Read AGENTS.md and relevant scheduling documentation.

Constraints:
Do not modify database records or unrelated modules.

Output:
Root cause, minimal correction, and verification steps.

Verification:
Run focused tests when available.
~~~

A good prompt specifies the outcome without micromanaging every reasoning step.

---

## 11. Avoiding Over-Prompting

Over-prompting adds detail that does not improve the task: generic principles, repeated requirements, multiple copies of the same architecture, or unnecessary output formatting.

It increases context use, possible conflicts, and maintenance effort.

Keep stable rules in AGENTS.md, reusable procedures in Agent Skills, and the current objective in the task prompt.

---

# Part V — Relevant File Selection

## 12. Why File Selection Matters

Reading an entire repository to fix one bug is rarely necessary. Locate the relevant module, inspect the primary file, trace direct dependencies, and read additional material only when evidence requires it.

~~~text
Understand Task → Locate Relevant Files → Inspect Primary File
               → Trace Dependencies → Read Relevant Docs
               → Implement or Review
~~~

---

## 13. File Discovery with PowerShell

~~~powershell
Get-ChildItem -Recurse -File
Get-ChildItem -Recurse -File -Filter "*.java"
Get-ChildItem ".\app\src\main" -Recurse -File
~~~

Recursive listing is useful for small repositories but can produce excessive output in larger projects. Narrow the search area before reading file contents.

---

## 14. Using ripgrep

ripgrep, commonly invoked as rg, is a fast text-search utility.

~~~powershell
rg --files
rg -n "ScheduleController" app
rg --files | rg "Schedule|Route"
rg -n "fetchProducts" --glob "*.ts" --glob "*.tsx"
~~~

It supports fast repository search, file filtering, and line-number output. It may not be installed in every environment; use available PowerShell or IDE search instead.

---

## 15. Search Before Reading

Inefficient: read many files, then search for the relevant function.

Efficient: search for the relevant symbol, identify candidate files, read those files, and trace necessary dependencies.

**Use search to locate information and file reading to understand it.**

---

# Part VI — Progressive Disclosure

## 16. What Is Progressive Disclosure?

Progressive disclosure loads detailed information only when relevant.

For an authentication bug, begin with AGENTS.md, authentication documentation, and relevant source files. Read the database schema if investigation reveals a database dependency.

~~~text
Task → Minimal Relevant Context → Initial Investigation
     → Need more information?
       ├── No: Proceed
       └── Yes: Load specific additional context
~~~

Load context incrementally instead of front-loading everything.

---

## 17. Progressive Disclosure in Agent Skills

Skills commonly use layered instructions:

~~~text
Skill Metadata → SKILL.md → Optional References
                              → Optional Scripts and Assets
~~~

For example, an Android UI skill can keep its main workflow in SKILL.md and load a detailed accessibility checklist only when needed. This avoids loading large references for every task.

---

# Part VII — AGENTS.md Efficiency

## 18. The Role of AGENTS.md

AGENTS.md provides persistent agent instructions, such as project purpose, stack, architecture, coding standards, scope, test commands, and documentation references.

~~~markdown
# Project Instructions

## Stack
Android Java and XML.

## Architecture
Follow the documented project structure.

## Scope
Implement only approved MVP features.

## Dependencies
Do not add libraries without justification.

## Documentation
Read the docs relevant to the current task.

## Verification
Run applicable checks and report results.
~~~

AGENTS.md should contain durable project rules, not a complete encyclopedia of the codebase.

---

## 19. Avoiding Bloated AGENTS.md Files

A bloated instruction file may contain the entire schema, every controller description, full API documentation, all UI specifications, testing history, and repeated standards.

Prefer concise core rules, a short architecture summary, and links to canonical documentation.

~~~markdown
## Architecture

Follow the documented MVC separation.

See:
- docs/architecture.md
- docs/database-schema.md
- docs/testing.md

Read only documentation relevant to the current task.
~~~

---

## 20. Avoiding Instruction Duplication

Repeated rules across AGENTS.md, coding standards, skills, and prompts increase token usage and can conflict.

| Information | Preferred Location |
|---|---|
| Repository-wide rules | AGENTS.md |
| Detailed architecture | docs/architecture.md |
| Reusable procedure | Agent Skill |
| Current objective | Task prompt |
| Feature decisions | Relevant feature documentation |
| Actual implementation | Source code and tests |

Reference canonical sources rather than copying their complete contents.

---

# Part VIII — Agent Skills Efficiency

## 21. When Skills Improve Efficiency

Skills are useful for workflows that are repeated, well-defined, task-specific, and expected to be consistent.

A code review skill can define steps such as inspect changed files, read project instructions, identify actionable issues, report evidence, and avoid editing.

---

## 22. When Skills Reduce Efficiency

A skill may be counterproductive if it is rarely used, excessively long, duplicates project instructions, loads irrelevant references, adds complex scripts for simple tasks, or has an overly broad trigger.

A dedicated skill for changing one button label is usually unnecessary.

---

# Part IX — Session Management

## 23. Context Accumulation

Long sessions accumulate exploration, debugging, tool output, implementation, testing, and revised plans. Earlier information may become irrelevant or outdated.

Problems include repeated logs, superseded hypotheses, conflicting decisions, and excessive history.

---

## 24. Session Hygiene

1. Keep the current objective clear.
2. Summarize important decisions.
3. Identify unresolved issues.
4. Avoid repeatedly pasting long logs.
5. Reference files instead of copying them.
6. Separate unrelated tasks.
7. Verify current repository state.
8. Preserve important information before switching sessions.

Preserve decisions and evidence, not every intermediate detail.

---

## 25. Context Compaction

Context compaction reduces carried context while preserving important state.

~~~text
Long Session → Identify Important State → Summarize
             → Smaller Working Context → Continue
~~~

Preserve the objective, approved scope, architecture decisions, changed files, executed tests, failures, constraints, and remaining tasks. Repeated tool output, superseded hypotheses, unrelated conversation, and duplicate explanations are often safe to omit.

Compaction differs across Codex CLI, Agents API, and other runtimes. Do not assume an API-level compaction parameter is a Codex CLI setting.

---

## 26. Manual Session Handoff

A concise handoff can help a new session resume:

~~~markdown
# Development Handoff

## Objective
Fix login layout alignment.

## Current Status
Layout inspection completed.

## Decisions
Preserve existing Java authentication logic.

## Relevant Files
- activity_login.xml
- colors.xml
- strings.xml

## Verification
Static layout review completed.
Device testing not yet performed.

## Remaining Work
Apply minimal XML correction and verify in Android Studio.
~~~

A focused summary avoids carrying the entire conversation forward.

---

# Part X — Tool-Call Efficiency

## 27. Why Tool Calls Matter

Agents search repositories, read files, execute commands, modify code, run tests, and retrieve documentation. Unnecessary calls increase time, context usage, and complexity.

Search for a target symbol, read relevant files, inspect dependencies, and run focused validation instead of listing and rereading the entire project.

---

## 28. Tool-Call Optimization

- Search before reading.
- Narrow directories.
- Reuse valid results.
- Batch related searches where supported.
- Run focused tests first.
- Expand investigation when evidence indicates a wider problem.

---

## 29. Avoiding Repeated Tool Calls

Do not repeatedly read unchanged files. Re-read when the file changed, new evidence changes the investigation, or verification needs current content. Preserve findings in working context.

---

# Part XI — Context Efficiency in Multi-Agent Workflows

## 30. Context Isolation

Subagents may use separate working contexts:

~~~text
Main Agent
    ├── UI Agent → UI Context
    └── Backend Agent → Backend Context
~~~

Isolation can focus each agent, but multiple agents may repeat repository exploration, instruction loading, tool calls, and reporting.

**Multi-agent delegation can improve focus but may increase total token consumption.**

---

## 31. Efficient Delegation

A good delegated task specifies objective, scope, relevant files, constraints, and expected output.

~~~text
Review ScheduleController.
Read applicable project instructions.
Inspect directly related services and validation.
Do not modify files.
Return findings with file references.
~~~

Avoid asking an agent to read the entire project when a focused review is sufficient.

---

# Part XII — Performance Tradeoffs

## 32. Efficiency Is Multidimensional

| Dimension | Meaning |
|---|---|
| Token efficiency | Avoid unnecessary model usage |
| Time efficiency | Reduce elapsed duration |
| Tool efficiency | Avoid redundant operations |
| Context quality | Preserve relevant information |
| Accuracy | Produce correct results |
| Maintainability | Keep workflows understandable |
| Verification | Confirm outcomes with evidence |

Reducing tokens is not an improvement if it makes work incorrect or incomplete.

---

## 33. Example Tradeoff

Approach A: “Fix login.” It is short but ambiguous and may cause repeated investigation.

Approach B: “Fix the login layout alignment. Only modify the XML layout and directly related resources. Preserve authentication behavior. Follow AGENTS.md. Verify layout constraints.” It is longer but clearer and may reduce rework.

The shortest prompt is not always the most efficient.

---

## 34. A Conceptual Efficiency Model

~~~text
Effective Efficiency =
Useful Verified Progress
------------------------
Time + Resource Consumption
~~~

This is an illustration, not a standardized metric. The objective is verified progress, not simply minimizing model activity.

# Part XIII — Practical Android Example

## 35. GroupTrack — Context-Efficient UI Development

For an approved sign-in UI, avoid asking Codex to read the entire project and history. Instead, direct it to AGENTS.md, relevant UI documentation, existing authentication layouts, and referenced resources.

~~~text
Task:
Implement the approved sign-in UI.

Context:
Read AGENTS.md, relevant UI documentation,
and existing authentication layout resources.

Scope:
Only the sign-in XML layout and directly related UI resources.

Constraints:
- Java/XML project.
- No unnecessary libraries.
- Do not modify Firebase authentication logic.
- Follow documented MVP scope.

Verification:
Check resource references and constraints.
Report whether preview or device testing occurred.
~~~

Workflow: read instructions, read relevant docs, inspect the layout and resources, make minimal changes, verify. Unrelated Firebase modules are unnecessary unless the task reveals a dependency.

# Part XIV — Practical Laravel Example

## 36. GoPasig — Context-Efficient Backend Investigation

For schedule validation, begin with the ScheduleController, direct services, model, validation rules, and relevant tests. Expand only when evidence requires it.

~~~text
Investigate the reported schedule validation issue.
Read AGENTS.md and relevant scheduling docs.
Start with ScheduleController and direct dependencies.
Do not inspect unrelated modules without evidence.
Do not modify database records.
Identify the root cause and minimal correction.
Run focused tests when available.
~~~

Search examples:

~~~powershell
rg -n "ScheduleController" app routes tests
rg -n "lockForUpdate|validate|schedule" app/Services
~~~

Search results identify candidates; they do not replace understanding the implementation.

# Part XV — Practical Next.js Example

## 37. E-commerce — Context-Efficient Frontend Debugging

If a product listing does not display API data, begin with the page, product components, API request function, TypeScript types, and relevant response shape. Inspect Laravel backend files only if evidence suggests an API mismatch.

~~~text
Investigate why the product listing page does not display API data.
Start with the Next.js product page, components, API client, and types.
Inspect backend response handling only if necessary.
Do not redesign unrelated pages.
Do not change the API contract without identifying the mismatch.
Report root cause and verification.
~~~

~~~powershell
rg -n "fetchProducts|Product" app components lib
~~~

Adjust search directories to the actual repository.

# Part XVI — Common Mistakes

## 38. Mistake: Reading the Entire Repository

**Problem:** Unnecessary files consume context.
**Improvement:** Search first, then inspect relevant files and dependencies.

## 39. Mistake: Excessively Short Prompts

**Problem:** Requirements are omitted.
**Improvement:** Include objective, scope, constraints, and verification.

## 40. Mistake: Bloated AGENTS.md

**Problem:** Persistent instructions contain excessive details.
**Improvement:** Keep core rules concise and link to canonical docs.

## 41. Mistake: Duplicating Documentation

**Problem:** Copies become inconsistent.
**Improvement:** Assign one authoritative location to each topic.

## 42. Mistake: Too Many Skills

**Problem:** Minor actions become separate workflows.
**Improvement:** Create skills only for genuinely reusable procedures.

## 43. Mistake: Repeating Tool Calls

**Problem:** Unchanged information is retrieved repeatedly.
**Improvement:** Preserve findings and re-read only when needed.

## 44. Mistake: Excessive Multi-Agent Delegation

**Problem:** Agents overlap or repeat investigation.
**Improvement:** Delegate independent tasks with clear boundaries.

## 45. Mistake: Removing Essential Context

**Problem:** Important constraints are lost.
**Improvement:** Prioritize correctness and safety over prompt brevity.

## 46. Mistake: Treating Compaction as Perfect Memory

**Problem:** Details may not survive compaction.
**Improvement:** Preserve key decisions and evidence in durable documentation.

# 58. Key Takeaways

1. Context quality matters more than context quantity.
2. Context windows have limits; tokens are not words or code lines.
3. Input, output, and reasoning usage consume model resources.
4. Relevant context improves understanding; irrelevant context adds overhead.
5. Efficient prompts define objectives and constraints.
6. The shortest prompt is not always most efficient.
7. Search before reading and trace dependencies only as needed.
8. Progressive disclosure reduces unnecessary loading.
9. Keep AGENTS.md concise and documentation canonical.
10. Avoid duplicating instructions.
11. Use Agent Skills for repeatable workflows, not every task.
12. Long sessions require hygiene and useful handoffs.
13. Compaction may not preserve every detail.
14. Focus tool calls and avoid repeating valid searches.
15. Multi-agent isolation can improve focus but increase total usage.
16. Efficiency includes accuracy, time, resource use, and maintainability.
17. Removing essential constraints can make a workflow less efficient.
18. Optimize for reliable, verified progress with minimal unnecessary overhead.
